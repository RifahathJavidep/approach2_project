Section 1

🚀 How to Run

There are two ways to use the extraction pipeline: via the CLI or via the FastAPI server.

Option A — CLI Mode (Direct Extraction)

Run extraction on files defined in config.json
python extract_requirements.py

This reads config/config.json, finds the current_project, loads its input files, and extracts requirements to the output directory.

Option B — API Mode (FastAPI Server)

1. Start the FastAPI server
python app.py
2. (Optional) Start Celery Worker for async processing
celery -A celery_app worker --loglevel=info
3. (Optional) Start Flower dashboard to monitor tasks
celery -A celery_app flower --port=5555
4. Open API docs in browser
http://localhost:8000/docs

🔄 End-to-End Pipeline Flow

Here's what happens when you run an extraction — whether via CLI or API.

COMPLETE DATA FLOW
📁 Input Files (S3 or Local) → 🔍 File Router → 📄 Extractors
→ → → → ↓
Text Content + 🖼️ Images → OCR → Verify → Classify → Analyze
↓
🤖 DSPy Extractor → Classifier → De-merger → Dedup + Consolidate
↓
📊 Requirements JSON → S3 + Java Backend
Step-by-step Execution Flow
📥

1. Input Files Received

API mode: Frontend uploads files to S3, sends S3 URLs to /extract. The server downloads files to a temp directory.
CLI mode: Reads files from the project's input_dir defined in config.json.

app.py → download_from_s3()
🔍

2. File Classification (Stage 1)

Each file is classified by extension and content analysis: PDF, DOCX, PPTX, Image, or Scanned PDF. This determines which extractor is used.

extraction/file_router.py → FileRouter.classify()
📄

3. Content Extraction (Stage 2)

Format-specific extractors pull text AND embedded images from each document. PDFs use pymupdf4llm, DOCX uses python-docx, PPTX uses python-pptx.

extraction/extractors/pdf_extractor.py
🖼️

4. Image Processing Pipeline

Each embedded image goes through: PaddleOCR → Vision Verify (Groq Llama 3.2 Vision corrects OCR errors) → Image Classify (workflow or informational?) → Diagram Analyze (extract graph structure from workflows).

extraction/processors/
🤖

5. AI Requirement Generation (Stage 3)

Combined text (document + image OCR + diagram narratives) is chunked and fed to the DSPy TrainedExtractor. Each requirement is classified (real vs noise), then composite requirements are de-merged into granular items.

extraction/generators/trained_extractor.py
🧹

6. Postprocessing

Requirements are deduplicated using Jaccard similarity, then consolidated via LLM to merge overlapping items. Each requirement gets a unique ID (e.g., PTW-001).

extraction/generators/postprocessing.py
☁️

7. Output & Storage

Results are: (a) uploaded to S3 as requirements.json, (b) model state saved locally, (c) requirements pushed to the Java backend (Postgres). The API returns the full JSON response.

app.py → upload_json_to_s3()
Section 3

🔍 Stage 1 — File Classification

S1

FileRouter

Identifies the file type and routes it to the correct extractor. For PDFs, it also checks if the document is scanned (no text layer) by attempting text extraction on the first 3 pages.

PDF
.pdf files with a text layer → pymupdf4llm
Scanned PDF
.pdf with <100 chars of text → PaddleOCR renders each page as image
DOCX
.docx, .doc → python-docx paragraph extraction
PPTX
.pptx, .ppt → python-pptx slide-by-slide extraction
Image
.png, .jpg, .jpeg, .svg, .gif, .webp, .bmp → Direct OCR + Vision
Unknown
Unsupported formats → Skipped with a warning
Section 4

📄 Stage 2 — Content Extraction

S2

Format-Specific Extractors

Each extractor provides two methods: extract_text() for document text and extract_images() for embedded images. Small images (<1KB) like icons are automatically filtered out.

pdf_extractor.py
Uses pymupdf4llm for markdown-formatted text extraction. Falls back to PaddleOCR for scanned PDFs (renders pages at 200 DPI). Extracts embedded images via PyMuPDF xref.
docx_extractor.py
Reads all paragraphs via python-docx. Extracts images from document relationships. Skips EMF/WMF formats (unsupported by Vision APIs).
pptx_extractor.py
Goes through each slide, extracts text from all shapes (titles, text boxes, placeholders). Extracts images from picture-type shapes with slide number tracking.
ocr_extractor.py
PaddleOCR wrapper supporting file paths, PIL Images, and base64. Returns text + confidence scores + bounding boxes. Replaces the old pytesseract dependency.
Section 5

🖼️ Image Processing Pipeline

This is the new capability — handles embedded images and workflow diagrams that were previously ignored entirely.

🖼

4-Step Image Pipeline

🖼️ Image → OCR (PaddleOCR) → Verify (GPT-4o) → Classify
→ → → → ↓ split
Informational → Use OCR text | Workflow → Diagram Analyzer → Narrative
vision_verifier.py
Sends image + OCR text to Groq Llama 3.2 Vision. The LLM compares OCR output against the image and corrects errors. Especially useful for complex layouts, handwriting, and small labels.
image_classifier.py
Uses Groq Llama 3.2 Vision to classify images as "workflow" (flowcharts, process diagrams) or "informational" (screenshots, tables, charts). Determines the next processing step.
diagram_analyzer.py
Uses Groq Llama 3.2 Vision to extract graph structure from workflow diagrams: nodes, connections, decision points, flow paths. Converts the graph into a readable text narrative for DSPy.
ocr_extractor.py
PaddleOCR — local OCR engine. No API calls needed. Downloads models (~150MB) on first use. Supports angle classification for rotated text.
Section 6

🤖 Stage 3 — AI Requirement Generation

S3

DSPy-Powered Extraction

Uses Groq LLaMA 3.3 70B for text extraction via DSPy framework, and Groq Llama 4 Scout for image understanding. Trained per-project using BootstrapFewShot.

signatures.py
RequirementExtraction: Extracts all business requirements across 3 layers (Features, UI, Workflows).
RequirementClassifier: Validates if a candidate is a real requirement or noise.
RequirementDeMerger: Splits composite requirements into granular items.
RequirementConsolidation: Merges truly redundant requirements.
trained_extractor.py
The TrainedExtractor DSPy Module chains: Extract → Pre-filter (skip keywords) → Classify (yes/no) → De-merge → Enrich with fallback fields. Returns accepted + filtered-out lists.
training.py
9 positive examples (CRM, Healthcare, General) + 11 negative examples (technical noise). Domain-weighted: healthcare/fintech examples get 2× weight for matching projects. Multi-project training scans other projects' PDFs.
postprocessing.py
Dedup: Jaccard similarity (title + full text) with threshold 0.55.
Consolidation: LLM-based merge for >45 items. Processes in batches of 60 with cross-batch merge for >100 items.
Section 7

🌐 API Endpoints (FastAPI)

All endpoints are served at http://localhost:8000. Interactive OpenAPI docs at /docs.

API

Available Endpoints

Method Endpoint Description
GET /health Health check — verifies API keys and Redis connection
POST /extract Synchronous extraction. Downloads from S3, extracts requirements, uploads results. Request: { project_id, file_urls[] }
POST /extract-async Async extraction. Queues in Celery, returns task_id immediately. Same request body as /extract.
GET /status/{task_id} Check Celery task progress. Returns: PENDING, PROGRESS, SUCCESS, or FAILURE
GET /requirements/{project_id} Get cached requirements from S3 (no re-extraction)
POST /generate-upload-url Generate pre-signed S3 upload URL for frontend. Request: { project_id, filename }
Sync vs Async: Use /extract for small projects (1–3 files, <2 min). Use /extract-async for large projects — it returns immediately with a task_id you can poll via /status/{task_id}.
Section 8

☁️ AWS S3 Integration

S3 is used for both file input (uploads) and output (results storage).

S3

S3 Bucket Structure

prism-bucket/ ├── projects/ │ └── {project_id}/ │ ├── input/ │ │ ├── requirements.pdf ← Uploaded by frontend │ │ ├── workflow.pptx ← Uploaded by frontend │ │ └── diagram.png ← Uploaded by frontend │ ├── output/ │ │ └── requirements.json ← Generated by pipeline │ └── models/ │ └── classifier_model.json ← Trained model backup

Upload Flow (Frontend → S3)

Frontend → POST /generate-upload-url → Pre-signed URL
Frontend → PUT to Pre-signed URL → File in S3 ✓
Security: AWS credentials are never exposed to the frontend. The backend generates time-limited pre-signed URLs (via /generate-upload-url) that the frontend uses for direct S3 uploads. Keys stay on the server.
Section 9

⚡ Async Processing (Celery + Redis)

⚡

Background Task Architecture

Frontend → POST /extract-async → Redis Queue → Celery Worker
Frontend → GET /status/{task_id} → PENDING | PROGRESS | SUCCESS | FAILURE

Celery worker runs in a separate process (celery -A celery_app worker). It imports extract_from_files from extract_requirements.py and processes the extraction in the background. Results are stored in Redis and uploaded to S3.

Task timeout: 1 hour maximum. Model state is saved locally to models/{project_id}/classifier_model.json.
